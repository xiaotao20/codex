# 抖音博主视频采集与总结工作流设计

## 1. 背景与目标

目标是构建一套可持续运行的自动化工作流，按固定时间抓取指定抖音博主的新视频，提取视频相关数据与口播文案，最终生成结构化总结和日报输出。

首期优先目标：

- 使用 GitHub Actions 作为定时调度入口
- 支持配置多个博主
- 支持按 `video_id` 去重
- 保存视频基础指标，例如点赞数、评论数、分享数、发布时间
- 将视频音频转写为文本
- 基于 OpenAI 生成结构化摘要、文案整理结果与总结
- 输出可下载的日报文件

非目标：

- 首期不追求复杂可视化后台
- 首期不做实时采集，只做定时批处理
- 首期不把模型结果直接回写到第三方系统
- 首期不将采集逻辑和平台强绑定，后续允许替换数据源

## 2. 设计原则

### 2.1 采集与分析解耦

数据采集层只负责获取原始视频数据，不负责总结、改写或判断内容质量。AI 分析层只消费标准化后的数据结构。

### 2.2 平台适配器可替换

抖音采集方案受页面结构、登录态、接口变化影响较大，因此必须做成适配器。当前开发版已经加入基于 `yt-dlp` 的真实采集适配器，用来验证主页抓取链路；后续如果改成第三方数据源、人工录入链接、或其他平台，业务主流程不需要重写。

### 2.3 输出结构化

总结结果不保存为纯自然语言段落，而是输出固定 JSON 结构，便于后续统计、筛选、报表和二次加工。

### 2.4 先离线批处理，再扩展通知

首期重点是把抓取、转写、分析、汇总跑通。消息通知、看板展示、跨团队分发放在后续迭代。

## 3. 总体架构

```text
GitHub Actions(schedule / workflow_dispatch)
  -> 加载配置
  -> 抓取博主视频列表
  -> 过滤新视频 / 去重
  -> 准备视频文件或音频
  -> 音频转写
  -> 调用 OpenAI 输出结构化结果
  -> 生成日报
  -> 上传 artifacts
```

建议模块划分：

```text
.github/workflows/
  douyin-daily.yml

code/douyin-workflow/
  app/
    main.py                # 流程入口
    config.py              # 配置读取
    logging_setup.py       # 日志初始化
    models.py              # 数据结构定义
    storage.py             # 本地状态和去重信息
    fetch/
      base.py              # 采集接口定义
      douyin_adapter.py    # 抖音适配器
    media/
      downloader.py        # 下载视频/音频
      audio.py             # 音频抽取与切片
    ai/
      transcribe.py        # 语音转写
      analyze.py           # 总结与结构化提取
    report/
      daily_report.py      # 日报生成
  config/
    creators.yaml
  outputs/
    raw/
    transcripts/
    analysis/
    reports/
    logs/
    state/
```

## 4. 核心流程设计

### 4.1 调度层

GitHub Actions 提供两个触发方式：

- `schedule`：按 cron 定时执行
- `workflow_dispatch`：手动触发补跑

建议首期每天执行 1 到 4 次，不要过于密集，先观察抓取成功率和配额消耗。

### 4.2 配置层

`code/douyin-workflow/config/creators.yaml` 示例：

```yaml
creators:
  - creator_id: chenxx
    name: 某博主
    homepage: https://www.douyin.com/user/xxxxx
    enabled: true
  - creator_id: linxx
    name: 另一位博主
    homepage: https://www.douyin.com/user/yyyyy
    enabled: true
```

配置只保存业务标识和主页信息，不保存密钥。敏感信息统一放到 GitHub Secrets。

### 4.3 采集层

采集层输出统一的视频元数据结构：

```json
{
  "creator_id": "chenxx",
  "creator_name": "某博主",
  "video_id": "7480000000000000000",
  "title": "视频标题",
  "publish_time": "2026-06-26T08:30:00+08:00",
  "video_url": "https://...",
  "cover_url": "https://...",
  "like_count": 12345,
  "comment_count": 345,
  "share_count": 67,
  "collect_count": 0
}
```

说明：

- `like_count`、`comment_count` 等属于原始采集字段，不依赖 AI 生成
- 若部分字段暂时拿不到，允许为空，但结构必须稳定
- 首期建议在采集结果中保留原始响应快照，便于排查字段变化

### 4.4 去重策略

首期使用本地状态文件或 SQLite 保存已处理的 `video_id`。

状态至少包含：

- `video_id`
- `creator_id`
- `fetch_time`
- `publish_time`
- `transcribe_status`
- `analyze_status`
- `report_status`

去重原则：

- 同一个 `video_id` 默认只进入完整分析一次
- 若只采集到了元数据但分析失败，允许下次重试分析阶段
- 若视频的互动数据需要更新，可单独设计“补采指标”模式

### 4.5 媒体处理层

媒体层职责：

- 下载视频或直接获取音频
- 使用 `ffmpeg` 抽取音轨
- 按时长或大小切片，避免超出转写接口限制

当前开发版已经实现独立的 `media` 阶段，支持三种输入：

- 直接提供 `audio_path`
- 提供 `local_media_path`
- 提供 `media_url`

建议输出：

- 原始媒体文件路径
- 抽取后的音频文件路径
- 音频时长
- 是否切片

### 4.6 转写层

转写层调用 OpenAI 语音转文字接口，输入为音频文件，输出为：

- `transcript_raw`：原始转写内容
- `transcript_clean`：必要的清洗结果，例如去除明显重复噪声
- `segments`：可选，保留时间戳切片

若视频无明显口播，可将字幕文本、标题、话题标签与 OCR 结果一起作为分析输入。

### 4.7 分析层

分析层基于视频元数据和转写文本，输出固定结构：

```json
{
  "summary": "一句话总结视频主题",
  "clean_copy": "整理后的文案",
  "hooks": ["开头钩子 1", "开头钩子 2"],
  "key_points": ["核心观点 1", "核心观点 2"],
  "keywords": ["关键词 1", "关键词 2"],
  "tone": "干货",
  "cta": "结尾引导动作",
  "content_type": "口播/剧情/带货/知识分享",
  "risk_notes": ["信息可能不完整"]
}
```

分析层的输入建议包括：

- 视频标题
- 话题标签
- 发布时间
- 互动数据
- 转写文本

分析层不负责虚构数据，不负责推断无法从素材中确认的事实。

### 4.8 报告层

日报输出建议同时生成两类文件：

- `report_YYYY-MM-DD.md`
- `report_YYYY-MM-DD.json`

日报内容建议包含：

- 当日新增视频数
- 各博主新增视频数
- 点赞数 Top N
- 评论数 Top N
- 每条视频的一句话总结
- 高频关键词
- 爆款内容共性观察

首期通过 GitHub Actions Artifact 提供下载，不直接推送到飞书或企业微信。

## 5. GitHub Actions 方案

### 5.1 工作流目标

使用 GitHub Actions 作为统一入口，负责：

- 定时触发
- 安装依赖
- 执行主流程
- 保留日志和报告产物

### 5.2 工作流建议

```yaml
name: douyin-daily-pipeline

on:
  schedule:
    - cron: '0 1 * * *'
  workflow_dispatch:

concurrency:
  group: douyin-daily-pipeline
  cancel-in-progress: false

jobs:
  run:
    runs-on: ubuntu-latest
    timeout-minutes: 60
    defaults:
      run:
        working-directory: code/douyin-workflow
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.11'
      - run: pip install -r requirements.txt
      - run: python -m app.main --mode all
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: douyin-report
          path: code/douyin-workflow/outputs/
```

### 5.3 Secrets 设计

建议至少配置以下 Secrets：

- `OPENAI_API_KEY`
- `DOUYIN_COOKIE`
- `DOUYIN_USER_AGENT`

如果后续接通知，还可增加：

- `FEISHU_WEBHOOK`
- `WECOM_WEBHOOK`

### 5.4 状态持久化策略

GitHub-hosted runner 不适合作为长期状态存储。首期可选两种路径：

#### 方案 A：仓库内状态文件

将 `code/douyin-workflow/outputs/state/processed.json` 回写仓库，再由工作流自动提交。

优点：

- 实现简单
- 便于查看历史变更

缺点：

- 定时任务会持续产生提交
- 状态文件逐渐膨胀
- 不适合高频运行

#### 方案 B：外部持久化

将去重状态放到 SQLite 文件、对象存储或云数据库中。

优点：

- 更适合长期运行
- 结构化程度更高

缺点：

- 首期接入成本更高

首期建议使用“状态文件 + artifact 报告”快速验证流程；进入稳定期后再迁移到外部持久化。

## 7. 错误处理与重试

需要区分三类失败：

### 7.1 采集失败

- 页面结构变化
- Cookie 失效
- 网络错误
- 被限流

策略：

- 单个博主失败不影响整个批次
- 保留错误日志和原始响应片段
- 限次重试，例如 2 次

### 7.2 转写失败

- 文件下载不完整
- 音频格式异常
- 文件过大
- 上游接口异常

策略：

- 对单个视频进行重试
- 对过大音频自动切片
- 标记状态，留待下次补跑

### 7.3 分析失败

- 模型调用超时
- 输出 JSON 不符合结构
- 输入文本为空

策略：

- 对模型调用启用重试
- 使用严格 JSON schema 校验
- 校验失败时记录原始返回内容

## 8. 日志与可观测性

建议按运行批次生成日志目录：

```text
code/douyin-workflow/outputs/logs/2026-06-26/
```

日志至少记录：

- 工作流开始与结束时间
- 每个博主的采集数量
- 每个视频的处理状态
- OpenAI 调用次数与失败次数
- 最终报告生成路径

首期不接入专门监控平台，以文件日志和 Actions 运行日志为主。

## 9. 安全与合规边界

### 9.1 密钥管理

- API Key、Cookie、Webhook 只放 GitHub Secrets
- 不写入代码、配置文件或提交记录

### 9.2 平台规则

抖音数据获取方式需要遵守目标平台规则、登录态要求、以及适用法律法规。技术设计上应避免把业务核心流程与某一种脆弱抓取方式深度耦合。

### 9.3 内容准确性

AI 生成的摘要和整理文案仅作为辅助结果，不应替代原始素材核验。日报中应保留来源视频标识与原始字段，便于追溯。

## 10. 开发阶段拆分

建议分四期推进：

### 第一期：骨架跑通

- 建立项目目录
- 建立 GitHub Actions 工作流
- 支持读取配置
- 接入占位采集器
- 接入状态文件去重
- 生成空白报告

交付标准：

- Actions 可以按计划执行
- 输出日志与占位报告

### 第二期：采集与转写打通

- 接入抖音适配器
- 下载媒体
- 抽取音频
- 调用转写接口

交付标准：

- 能稳定获取新视频并产出转写文本

### 第三期：分析与汇总

- 接入结构化总结
- 生成 JSON 与 Markdown 日报
- 增加 Top 排行与关键词统计

交付标准：

- 每条视频可生成结构化分析结果
- 每天可产出可阅读日报

### 第四期：增强能力

- 飞书/企业微信通知
- 外部数据库持久化
- 增量指标回补
- 人工复核与修订流程

## 11. 当前建议的实施顺序

下一步开发阶段建议按以下顺序落地：

1. 先搭项目骨架和 GitHub Actions
2. 先用本地假数据和本地种子数据验证去重、媒体准备、报告、Artifacts
3. 再接入真实采集器
4. 接着接 OpenAI 转写
5. 最后接结构化总结和日报优化

这样做的原因是，最容易变化的是采集层，最不应该最早写死的也是采集层。先把主流程跑通，后续替换数据源的成本最低。

## 12. 待确认事项

进入开发前，建议确认以下决策：

- 是否接受首期使用“状态文件”而不是数据库
- 抖音数据来源是页面抓取、现有接口，还是第三方数据源
- 是否需要在日报中展示“原始转写全文”
- 是否需要保留视频文件，还是只保留音频与分析结果
- GitHub Actions 计划每天跑几次
- 是否需要后续接入飞书或企业微信通知

本设计文档用于第一阶段开发基线。若数据源、部署方式或持久化方案变化，应优先更新本文档后再进入实现。
