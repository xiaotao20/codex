# Codex 常用方式

这份文档给刚开始使用 Codex 的人，重点不是“把所有功能都讲完”，而是先把最常用、最容易上手的方式写清楚。

## 1. 先选一个入口

| 方式 | 适合场景 | 你会得到什么 |
| --- | --- | --- |
| CLI | 在仓库根目录里读代码、改代码、跑命令 | 适合真实开发，命令、diff、验证都在一个会话里 |
| IDE 扩展 | 一边看代码一边和 Codex 交互 | 打开的文件和选中代码会自动成为上下文，提问更短 |
| App | 同时跟多个项目、多个线程协作 | 并行线程、worktree、automations、Git 功能更集中 |
| Cloud | 后台长任务、跨设备继续、并行执行 | 让 Codex 在云端环境里跑任务，适合长时间任务 |

如果你刚开始用，建议顺序是：

1. 先用 CLI
2. 再尝试 IDE 扩展
3. 真正需要后台并行和跨设备时再用 Cloud
4. 当你开始同时管多个线程、多个项目时再用 App

## 2. 新手最稳的起步方式

### 第一步：在仓库根目录启动

最稳的默认组合通常是：

```bash
codex --ask-for-approval on-request --sandbox workspace-write
```

这套配置的含义很简单：

- 工作区内的读写和常规命令可以自动执行
- 超出工作区或需要联网时，再向你请求批准
- 比一开始就开到全权限更适合日常开发

### 第二步：先让它解释项目，不急着改

```text
请先阅读这个仓库，告诉我：
1. 主要目录和职责
2. 入口文件在哪里
3. 当前项目如何启动和测试
4. 你认为最值得先看的 3 个文件
```

### 第三步：第二轮再给一个明确任务

最推荐的结构是：

```text
Goal:
修复设置页保存后刷新丢失的问题

Context:
- 相关文件：src/settings.ts, src/api.ts
- Repro:
  1. npm run dev
  2. 打开 /settings
  3. 修改开关并点击保存
  4. 刷新页面后配置丢失

Constraints:
- 不改 API 结构
- 修复尽量最小
- 能补测试就补最小回归测试

Done when:
- 问题不能再复现
- 运行最小相关测试
- 输出修改摘要和验证结果
```

如果任务比较大，先加一句：

```text
先不要写代码，先给我一个最小可执行计划。
```

## 3. 最常用的几种工作方式

### 读懂陌生仓库

```text
请先阅读这个仓库，重点看 README 和你认为最关键的入口文件。
输出：
1. 系统结构
2. 启动方式
3. 核心模块
4. 修改时最容易踩坑的地方
```

适合刚接手老项目，或者你对某个模块完全不熟的时候。

### 修一个可复现的 bug

```text
Bug:
点击 Save 后提示成功，但刷新页面后数据没有持久化。

Repro:
1. npm run dev
2. 打开 /settings
3. 修改开关
4. 点击 Save
5. 刷新页面，修改丢失

Context:
- 我怀疑问题在 @src/settings.ts 和 @src/api.ts

Constraints:
- 不要改 API 结构
- 修复尽量最小
- 修复后运行最小相关验证
```

这种写法比“帮我修一下”稳定很多。

### 做一个小功能

```text
Goal:
给后台订单列表加一个 CSV 导出按钮

Context:
- 相关文件：@src/orders/list.tsx, @src/orders/api.ts
- 当前已经有筛选、分页和 JSON 导出

Constraints:
- 不改现有 JSON 导出行为
- 不新增生产依赖
- UI 风格沿用当前项目

Done when:
- 页面可以导出当前筛选结果
- 相关测试通过
- 输出改动摘要和验证结果
```

### 做代码审查

```text
请基于当前 diff 做一次代码审查。
优先指出：
1. 可能的 bug
2. 回归风险
3. 缺失测试
4. 可以缩小的改动面
```

### 写文档或 README

```text
请先阅读 README 和相关实现文件。
为这个模块补一份最小可执行中文说明，包含：
1. 作用
2. 启动方式
3. 关键配置
4. 常见问题
完成后检查链接和命令是否可执行。
```

## 4. 最常用命令

### CLI 启动

```bash
codex
```

直接带上初始任务也可以：

```bash
codex "Explain this codebase to me"
```

### 切到某个目录再启动

```bash
codex --cd <path>
```

### 给工作区外的额外目录授权

```bash
codex --add-dir <path>
```

### 临时切模型

```bash
codex --model <model_name>
```

### 开启实时网页搜索

```bash
codex --search
```

## 5. 交互里最常用的操作

### CLI 里记住这几个就够用了

- `/model`
  - 切模型
- `/permissions`
  - 调整当前会话的批准策略
- `/agent`
  - 处理代理/线程相关操作
- `/status`
  - 看当前线程状态
- `/clear`
  - 清空界面并开始新会话
- `/copy`
  - 复制最近一次完成的输出

另外两个小技巧很好用：

- 输入 `/` 可以打开 slash command 列表
- 如果 Codex 正在执行任务，按 `Tab` 可以把下一条文本、命令或 slash command 排队到下一轮

## 6. CLI、IDE、App、Cloud 怎么分工

### CLI

最适合：

- 真正进入仓库工作
- 需要看命令输出、diff、测试结果
- 需要完整会话记录

### IDE 扩展

最适合：

- 你已经在 VS Code、Cursor、Windsurf 这类编辑器里工作
- 希望打开文件和选区自动成为上下文
- 希望边改边看预览和变更

如果你是在 IDE 里用 Codex，很多情况下你可以把提示词写得更短，因为打开的文件和选中代码会自动被带进去。

### App

最适合：

- 同时跟进多个任务
- 想集中看多个线程
- 想把 worktree、automations、Git 这些能力放到一个桌面入口里

### Cloud

最适合：

- 跑长任务
- 后台并行执行
- 换设备继续

如果你要让 Codex 在云端直接处理你的仓库，先把代码推到 GitHub 会更顺。

## 7. 两个最值得先配的文件

### `~/.codex/config.toml`

这是你的个人默认配置。一个够用的起点可以是：

```toml
model = "gpt-5.5"
approval_policy = "on-request"
sandbox_mode = "workspace-write"
```

补充两点：

- CLI 和 IDE 扩展共享这套配置层
- 项目级覆盖可以放在 `.codex/config.toml`

### `AGENTS.md`

这是“这个仓库希望 Codex 怎么工作”的说明文件，适合写：

- 修改前后要跑什么命令
- 哪些目录不能动
- 文档放哪里
- 提交前要做什么检查
- 是否允许加新依赖

一个最小例子：

```md
# AGENTS.md

## Repository expectations

- Run `npm run lint` before opening a pull request.
- Ask before adding new production dependencies.
- Keep docs in `docs/`.
```

## 8. 新手最容易踩的坑

1. 一上来就给一个太大的任务
2. 不写复现步骤、约束、完成标准
3. 在 CLI 里不主动给文件路径
4. 同时开多个线程改同一批文件
5. 不要求 Codex 自己做验证
6. 不看 diff 就直接提交

## 9. 一句最实用的建议

本地改代码，优先用 CLI 或 IDE；要后台长任务、跨设备继续、并行处理，再用 Cloud；开始同时管理多个线程和项目时，再把 App 用起来。
