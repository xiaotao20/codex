# 使用 Codex 在原项目上开发新需求

这不是“从零生成一个 demo”的教程，而是一份面向真实工作场景的开发手册：

- 目标是基于现有代码仓库开发新需求
- 输出要求接近生产级别代码
- 强调可验证、可评审、可回滚、可持续协作

如果你是第一次接触 Codex，先看 [入门教程.md](./入门教程.md)。这篇文档默认你已经能启动 Codex，并希望把它真正用在日常研发里。

## 1. 先建立正确预期

在真实项目里，Codex 最适合扮演的是一个会行动的工程搭档，而不是一个“自动生成答案”的聊天机器人。

它的强项是：

- 读懂陌生代码仓库
- 沿着现有结构实现需求
- 根据你的约束补代码、补测试、补文档
- 跑命令、检查 diff、整理变更

它的上限，往往取决于你是否把以下几件事说清楚：

- 需求边界
- 相关上下文
- 架构约束
- 验证方式
- 完成标准

对于高风险或复杂改动，先让 Codex 做计划，再让它实现，通常比“一步到位直接写”更稳。

## 2. 生产环境下的基本原则

### 原则一：永远以现有仓库为中心

在原项目上开发新需求，重点不是“能不能写出来”，而是：

- 是否贴合现有目录结构
- 是否复用现有模式
- 是否兼容已有行为
- 是否满足测试和发布流程

你应该要求 Codex 优先遵守仓库现有约定，而不是重新发明一套结构。

### 原则二：先定义 done，再开始编码

对 Codex 最有效的任务描述，通常不是“帮我加一个功能”，而是：

```text
Goal:
为后台订单列表增加 CSV 导出功能

Context:
- 相关文件：src/orders/list.tsx, src/orders/api.ts
- 当前已有筛选、分页、JSON 导出
- 测试在 tests/orders/

Constraints:
- 不要改现有 JSON 导出行为
- 不新增生产依赖
- 保持接口向后兼容

Done when:
- 页面支持导出当前筛选结果
- 有最小相关测试
- lint / typecheck / 相关测试通过
```

这个结构比泛泛描述更适合真实项目，也更适合评审。

### 原则三：让它自己验证

如果你不要求验证，Codex 很容易停在“代码看起来差不多”这一层。

更稳的要求是：

- 运行最小相关测试
- 运行 typecheck / lint / build
- 给出手工验证步骤
- 如果无法运行，说明原因和影响

### 原则四：不要让两个线程同时改同一批文件

并行可以提升效率，但不要让多个线程同时修改同一组核心文件，否则冲突和回归风险会明显上升。

## 3. 进入生产项目前的准备

建议你在仓库根目录启动 Codex，并尽量保持安全边界清晰：

```bash
codex --sandbox workspace-write --ask-for-approval on-request
```

这套配置适合大多数本地开发场景：

- 允许在工作区内读写和运行常规命令
- 超出工作区或需要联网时再请求审批
- 比完全放开权限更适合真实项目

如果项目非常大，或者需要读工作区外的公共目录，再额外加：

```bash
codex --add-dir <path>
```

## 4. 开始一个新需求的标准流程

下面这套流程适合“已有线上项目，新增一个真实需求”。

### 第一步：先让 Codex 理解现状，不要马上写代码

第一轮建议这样开：

```text
先不要写代码。

请阅读这个仓库，重点关注与需求相关的目录和入口文件，然后输出：
1. 当前实现在哪里
2. 需求最可能影响哪些模块
3. 哪些部分是高风险区
4. 你建议的最小实现路径
5. 你准备如何验证
```

如果你已经知道关键文件，直接显式给它：

```text
请先阅读 @README.md、@src/orders/list.tsx、@src/orders/api.ts。
先不要改代码，先给我最小可执行方案。
```

### 第二步：复杂任务先做计划

对于以下任务，先计划再实现通常更稳：

- 改公共基础模块
- 涉及数据库或数据迁移
- 涉及接口兼容
- 涉及性能、权限、缓存、并发
- 涉及跨多个模块的改动

你可以直接这样说：

```text
先不要写代码。先给我一个计划：
1. 你理解的问题
2. 你打算改哪些文件
3. 每个文件改动的目的
4. 风险点
5. 验证方案
```

### 第三步：实现时把范围卡住

在生产项目里，最怕的是 Codex 一路扩散修改范围。

因此实现提示词最好主动限边界：

```text
现在开始实现。

要求：
- 只改和这个需求直接相关的文件
- 优先沿用现有实现风格
- 不做无关重构
- 如果需要新增文件，说明为什么必须新增
- 完成后运行最小相关验证
```

### 第四步：要求它补测试，而不是只补代码

新增需求若没有测试，后续维护成本会很快升高。

建议明确要求：

```text
实现功能后，请补最小必要测试：
- 优先补回归风险最高的路径
- 不为了覆盖率堆无效测试
- 如果当前仓库没有对应测试基础设施，就给出最小手工验证步骤
```

### 第五步：要求它做一次变更审查

在提交前，建议让 Codex 自己再审一遍：

```text
请基于当前 diff 做一次工程审查：
- 有没有破坏现有行为的风险
- 有没有遗漏的测试
- 有没有过度改动
- 有没有可以缩小的修改面
```

## 5. 一个可直接工作的生产级流程模板

下面是一套可以直接复制使用的完整话术。

### 模板 A：先梳理需求和方案

```text
目标：
在现有项目上实现一个新需求，但先不要写代码。

需求：
<在这里写清楚需求>

上下文：
- 仓库是存量项目，不是新项目
- 请优先遵循当前架构和编码风格
- 如果你不确定某个行为，请基于代码现状判断，不要臆测

输出要求：
1. 当前功能在哪里实现
2. 最可能需要修改的文件
3. 最小实现方案
4. 风险点
5. 测试计划
6. 回滚或降级思路
```

### 模板 B：进入实现

```text
现在开始实现。

约束：
- 保持现有公共接口兼容
- 不做无关重构
- 优先复用现有工具函数、组件和模式
- 如果要引入新依赖，先停下来说明理由
- 完成后运行最小相关验证

完成标准：
- 功能可用
- 相关测试更新
- lint / typecheck / 相关测试通过
- 输出修改摘要和验证结果
```

### 模板 C：只做测试补强

```text
不要改生产逻辑，只补测试。

目标：
为刚才这个需求补最小必要测试，优先覆盖：
1. 主路径
2. 边界输入
3. 最容易回归的分支

完成后请说明：
- 新增了哪些测试
- 每个测试防的是什么问题
- 还剩哪些风险
```

### 模板 D：只做审查

```text
不要再改代码。

请对当前改动做一次生产级审查：
1. 需求是否真正落地
2. 是否有兼容性风险
3. 是否有错误处理或边界条件遗漏
4. 测试是否足够
5. 是否存在可以缩小的改动面
```

## 6. 生产级代码应该额外检查什么

和 demo 代码相比，真实项目里的“完成”标准通常还应包含这些内容：

### 接口与兼容性

- 是否影响旧接口
- 是否影响历史数据
- 是否影响默认行为
- 是否需要 feature flag

### 验证与发布

- 单元测试是否覆盖核心逻辑
- 集成测试是否覆盖关键链路
- 是否需要补充手工验收步骤
- 是否需要更新文档、变更说明或运维手册

### 运行与回滚

- 失败时是否有明确错误信息
- 是否会留下半完成状态
- 是否容易回滚
- 是否需要额外日志、监控或埋点

### 修改面控制

- 是否改了不相关文件
- 是否把重构和功能改动混在一起
- 是否引入了不必要的新抽象

## 7. 让 Codex 更稳定的几个习惯

### 明确文件上下文

在 CLI 里，Codex 不会天然像 IDE 那样总能自动拿到你正盯着的文件。

所以你应该主动给路径，或者使用 `/mention` 把关键文件附加进去。

### 大任务拆成多轮

生产需求不要一口气要求“分析、设计、实现、补测试、写发布说明、推远程”。

更稳的拆法通常是：

1. 先理解现状
2. 再出方案
3. 再实现
4. 再补测试
5. 再审查
6. 最后提交

### 多用 `/diff`

提交前一定看 diff。

```text
/diff
```

这一步在真实工作里很关键，因为它能快速暴露：

- 误改无关文件
- 改动范围失控
- 临时调试代码未清理
- 测试遗漏

### 长会话适时压缩

项目任务做久了，上下文会变长。

这时可以用 `/compact` 保留关键上下文、压缩对话长度，避免后续轮次上下文噪声过大。

## 8. 推荐在仓库里准备的两个文件

### AGENTS.md

适合写“这个仓库默认怎么工作”，例如：

- 修改前后要跑哪些命令
- 哪些目录禁止改
- 是否允许加依赖
- 文档应该放哪里
- 提交前要做哪些检查

### .codex/config.toml

适合写“这个项目的默认运行配置”，例如：

```toml
model = "gpt-5.5"
approval_policy = "on-request"
sandbox_mode = "workspace-write"
```

如果团队对审批策略、默认模型、MCP 或额外目录权限有固定要求，可以把它们放进项目级 `.codex/config.toml`。

## 9. 推荐给团队的最小落地方式

如果你想把 Codex 真正用在工作里，而不是偶尔试试，最小可执行方案通常是：

1. 在仓库根目录维护 `AGENTS.md`
2. 把 lint、typecheck、test 写进明确命令
3. 大任务先计划，小任务直接实现
4. 每次任务结束都检查 diff
5. 每次涉及文件改动都单独提交
6. 让评审聚焦在需求正确性和风险，而不是让人肉去猜改动背景

## 10. 本仓库里可以直接采用的工作方式

这个仓库当前已经有 [AGENTS.md](../AGENTS.md)，可以继续扩展成团队规则文件。

你以后在这个仓库里给 Codex 下任务时，可以优先用下面这类说法：

```text
请先阅读相关文件，先不要写代码。
给我一个最小可执行方案、风险点和验证计划。
确认后再实现，并在有文件改动时完成一次清晰的 git commit。
```

如果你的目标是“在原项目里稳定迭代新需求”，这类工作方式通常比一次性大提示词更可靠。

## 11. 最后给一条很实用的判断标准

如果你准备把 Codex 产出的改动直接进入生产流程，至少问自己这 5 个问题：

1. 这个改动是否贴合现有架构，而不是另起炉灶？
2. 这个改动是否有明确验证，而不是只靠肉眼判断？
3. 这个改动是否控制了修改面？
4. 这个改动是否说明了风险和回滚方式？
5. 这个改动是否足够清晰，能被别人接手维护？

只要这 5 个问题里有两个答不上来，就先不要急着合并。
